## 1. Назначение проекта

Glossy — проект разработки нового коммерческого сайта для действующей компании «Космоавто112», работающей в Екатеринбурге.

Цель — создать современный, визуально качественный, адаптивный сайт, который:
- Презентует услуги компании.
- Демонстрирует реальные работы автосервиса.
- Показывает доступные автомобили для аренды.
- Помогает потенциальному клиенту быстро найти нужную информацию.
- Обеспечивает удобную связь с компанией.
- Формирует профессиональное впечатление о бизнесе.

Glossy — внутреннее название проекта разработки. Это не новое название компании и не изменение её бренда.

### 1.1. Основной принцип

Необходимо сохранить достоверность информации существующего бизнеса, но полностью переосмыслить визуальную подачу, структуру интерфейса и пользовательский опыт.

Исходный сайт:
https://kosmoavto112.ru/

Существующий сайт используется как источник информации и части фотографий. Информация о компании, услугах и ценах подтверждена заказчиком как актуальная.

Не придумывать:
- Количество лет работы.
- Количество обслуженных автомобилей.
- Отзывы клиентов.
- Гарантии, если они не подтверждены.
- Лицензии, сертификаты и награды.
- Неизвестные характеристики услуг и автомобилей.

## 2. Визуальная концепция

### 2.1. Утверждённое направление

**Light Minimal v1 — Light Minimalism.**

Визуальный стиль:
- Светлый.
- Минималистичный.
- Воздушный.
- Современный.
- Аккуратный.
- Профессиональный.
- Сдержанный, но не скучный.

Основная задача — добиться ощущения качественного коммерческого продукта, а не типового шаблонного сайта автосервиса.

Не использовать чрезмерное количество декоративных элементов, ярких градиентов, массивных теней и визуального шума.

### 2.2. Цветовая концепция

Light Minimal v1 использует централизованные дизайн-токены. Единственный источник конкретных значений — `docs/design/DESIGN_SYSTEM.md`; значения, размеры, breakpoints и шрифтовые настройки в нём пока имеют предварительный статус. Ориентиры цветов логотипа зафиксированы в `docs/design/DESIGN_SYSTEM.md` и также остаются предварительными.

Оранжевый используется дозированно:
- Основные CTA.
- Интерактивные элементы.
- Небольшие акценты.
- Индикаторы активного состояния.

Не превращать весь интерфейс в оранжевый.

### 2.3. Типографика

Предварительно утверждённый шрифт — Manrope.

Требования:
- Выразительные заголовки.
- Хорошая читаемость основного текста.
- Чёткая визуальная иерархия.
- Контролируемая длина строк.
- Адаптивные размеры шрифтов.
- Единая система начертаний и межстрочных интервалов.

Не задавать размеры шрифтов произвольно внутри отдельных компонентов.

### 2.4. Композиция

Предпочтения:
- Чистая сетка.
- Достаточное свободное пространство.
- Аккуратная асимметрия там, где она усиливает композицию.
- Крупные качественные фотографии.
- Контраст между заголовками и вспомогательным текстом.
- Единый ритм вертикальных отступов.

Основной визуальный ориентир — ранее согласованная версия Light Minimal v1. Не возвращаться к экспериментальной версии с чрезмерно декоративной композицией.

## 3. Структура сайта

Сайт представляет собой одностраничный коммерческий лендинг.

Содержательные секции:
1. Hero.
2. Services.

## 4. Подробное описание секций

### 4.1. Header

Назначение — навигация по сайту и быстрый доступ к основным контактам.

Состав:
- Логотип компании.
- Навигация по секциям.
- Контактная информация или телефон.
- Основная CTA-кнопка.

Поведение:
- На десктопе — горизонтальная навигация.
- На мобильных устройствах — компактная мобильная навигация.
- При прокрутке вниз Header скрывается.
- При прокрутке вверх Header появляется.
- При возвращении к началу страницы Header находится в исходном положении.
- Переходы должны быть плавными.
- Не допускать скачков содержимого при изменении положения Header.

Мобильная навигация:
- Имеет закрытое и открытое состояния.
- Открывается по нажатию на кнопку меню.
- Закрывается при выборе пункта.
- Закрывается по Escape.
- Не должна создавать горизонтальную прокрутку.
- Должна быть доступна с клавиатуры.

Активные пункты навигации должны соответствовать фактическому состоянию страницы, если для этого используется подсветка активной секции.

### 4.2. Hero

Главная секция, формирующая первое впечатление.

- Асимметричная.

- С крупным визуальным элементом или фотографией.
- С заметной основной CTA.
- С дополнительной информацией, если она помогает понять профиль компании.

Содержание должно быстро объяснять:
- Чем занимается компания.
- Какие основные услуги доступны.
- Как связаться или перейти к нужному разделу.

Требования:
- Не перегружать первый экран.
- Не использовать длинные рекламные тексты.
- Не придумывать неподтверждённые преимущества.
- На мобильном устройстве сохранять понятную иерархию.
- CTA должна вести к соответствующей секции или контактному действию.

## 5. Дизайн-система

Использовать существующий `docs/design/DESIGN_SYSTEM.md` как основной источник дизайн-токенов.

Обязательные группы токенов:
- Цвета.
- Фоны.
- Цвета текста.
- Границы и их толщины.
- Радиусы.
- Тени.
- Отступы.
- Размеры элементов.
- Контейнеры и сетка.
- Типографика.
- Анимации и переходы.
- Breakpoints.
- Z-index.

### 5.1. Централизация

Все повторно используемые значения должны находиться в едином источнике.

Основной механизм — CSS Custom Properties.

SCSS-переменные использовать для compile-time значений, функций и миксинов, но не создавать параллельные независимые палитры.

Не допускается:
- Дублирование одинаковых цветов в компонентах.
- Произвольные отступы без обращения к системе.
- Повторное объявление одинаковых радиусов.
- Разрозненные значения времени анимации.
- Локальные breakpoint-значения без необходимости.

Если возникает потребность в новом токене, сначала проверить существующую систему и добавить новое значение централизованно.

## 6. Техническая архитектура

Использовать согласованный стек и существующую архитектурную документацию.

Предварительно согласованный стек:

- React.
- TypeScript.
- Vite.
- React Router.
- SCSS.
- БЭМ.
- Material UI.
- React Hook Form.
- Zod.
- Vitest.
- React Testing Library.
- Playwright.
- ESLint.
- Prettier.

### 6.1. Ответственность технологий

**React**
- Компонентная архитектура.
- Управление состоянием интерфейса.
- Композиция секций.

**TypeScript**
- Типизация компонентов.
- Типизация данных.
- Типизация событий и обработчиков.
- Минимизация использования `any`.

**React Router**
- Управление маршрутами.
- Layout и вложенные маршруты, если они необходимы.
- Не усложнять одностраничный сайт искусственной маршрутизацией.

**SCSS + БЭМ**
- Собственные стили проекта.
- Стилизация секций.
- Адаптивная сетка.
- Визуальные эффекты.
- Состояния компонентов.

**Material UI**
- Использовать для подходящих готовых UI-примитивов.
- Не допускать визуального конфликта с утверждённой дизайн-системой.
- Не использовать MUI как замену индивидуальному дизайну сайта.

**React Hook Form + Zod**
- Управление формами.
- Валидация.
- Типизация данных формы.
- Единая схема проверки.

### 6.2. Архитектурные требования

- Разделять страницы, секции и переиспользуемые компоненты.
- Не создавать чрезмерно большие компоненты.
- Не дублировать бизнес-данные в JSX.
- Отделять данные от представления.
- Использовать понятные названия файлов и компонентов.
- Сохранять единый стиль проекта.
- Не вводить новые библиотеки без необходимости и обоснования.

Предпочтительно хранить повторяющиеся данные услуг, цен и автомобилей в отдельных типизированных структурах.

## 7. Адаптивность

Сайт должен корректно работать на:
- Больших десктопных экранах.
- Ноутбуках.
- Планшетах.
- Смартфонах.

Не ориентироваться исключительно на фиксированные размеры экранов.

Использовать адаптивную сетку, гибкие размеры и корректные ограничения ширины контента.

### Основные требования

**Десктоп:**
- Полноценная горизонтальная навигация.
- Выразительная композиция Hero.
- Карточки и секции с достаточным свободным пространством.
- Удобное использование мышью и клавиатурой.

**Планшет:**
- Перестроение колонок.
- Сохранение читаемости.
- Корректное поведение карточек и изображений.

**Мобильные устройства:**
- Мобильная навигация.
- Одна или две колонки там, где это оправдано.
- Удобные интерактивные области.
- Читаемые заголовки и текст.
- Отсутствие горизонтальной прокрутки.
- Оптимизированные изображения.
- Удобное взаимодействие с CTA.

Проверять не только стандартные breakpoint-размеры, но и промежуточные ширины.

## 8. Анимации и взаимодействия

Анимации должны улучшать восприятие и обратную связь, а не отвлекать от содержания.

Предусмотреть:

1. Плавное появление элементов при прокрутке.
2. Небольшие hover-эффекты карточек.
3. Плавные состояния кнопок.
4. Переходы Header при прокрутке.
5. Анимацию мобильной навигации.
6. Интерактивный слайдер «До / После».
7. Аккуратные переходы между состояниями форм.

### Ограничения

- Не использовать тяжёлые анимации без необходимости.
- Не анимировать большие объёмы элементов одновременно.
- Не допускать скачков layout.
- Не ухудшать производительность.
- Не блокировать взаимодействие пользователя анимациями.
- Учитывать `prefers-reduced-motion`.
- Предпочитать CSS-анимации для простых эффектов.
- Использовать JavaScript только там, где действительно нужна логика взаимодействия.

## 9. Формы и пользовательские сценарии

Форма обратной связи требует отдельного согласования.

До реализации необходимо уточнить:
- Какие поля нужны.
- Какие поля обязательны.
- Куда отправляются заявки.
- Как обрабатываются персональные данные.
- Какие согласия и юридические документы необходимы.

Нельзя создавать фиктивную отправку формы с сообщением об успешной отправке, если данные фактически никуда не передаются.

После согласования форма должна иметь состояния:
- Default.
- Focus.
- Validation error.
- Loading.
- Success.
- Submission error.

Валидацию выполнять через согласованную схему Zod.

## 10. Изображения и медиа

Основной источник фотографий — материалы существующего сайта и изображения, предоставленные заказчиком.

Требования:
- Не использовать случайные стоковые фотографии вместо реальных работ.
- Не изменять смысл фотографий.
- Сохранять правильные пропорции.
- Использовать подходящий `object-fit`.
- Оптимизировать размер файлов.
- Предусмотреть корректные alt-описания.
- Для изображений ниже первого экрана использовать отложенную загрузку, если это не ухудшает UX.

До получения новых фотографий использовать только доступные и проверенные материалы. Не придумывать содержимое фотографий.

## 11. SEO и производительность

### SEO

Предусмотреть:
- Корректный `title`.
- Meta description.
- Семантическую структуру заголовков.
- Семантические HTML-элементы.
- Alt для содержательных изображений.
- Open Graph metadata.
- Корректные ссылки и контактные данные.
- Favicon.
- Sitemap и robots.txt при подготовке production-развёртывания.

Не использовать заголовки исключительно ради визуального размера.

### Производительность

Учитывать:
- Оптимизацию изображений.
- Минимизацию лишних зависимостей.
- Разумное использование анимаций.
- Отсутствие ненужных повторных рендеров.
- Корректную загрузку шрифтов.
- Разделение кода там, где это оправдано.

Проверять Core Web Vitals и Lighthouse на реальной production-сборке, а не заявлять о высоких показателях без измерений.

## 13. Безопасность и персональные данные

Не хранить секреты в клиентском коде.

Не размещать API-ключи и приватные токены в репозитории.

Если форма будет отправлять данные на сервер или сторонний сервис:
- Проверять входящие данные.
- Не доверять только клиентской валидации.
- Использовать защищённый канал передачи.
- Не раскрывать внутренние ошибки пользователю.
- Не собирать лишние персональные данные.
- Согласовать юридическую обработку заявок.

Конкретная серверная архитектура формы пока не утверждена.

## 17. Критерии готовности

Проект можно считать готовым к production, когда:

- Все секции реализованы.
- Содержание соответствует действующей информации компании.
- Дизайн соответствует Light Minimal v1.
- Все повторно используемые значения централизованы.
- Desktop и mobile версии работают корректно.
- Навигация и CTA функционируют.
- Интерактивные элементы доступны с клавиатуры.
- Нет фиктивной отправки форм.
- Изображения оптимизированы.
- SEO-метаданные настроены.
- Нет критических ошибок в консоли.
- TypeScript и ESLint проходят проверки.
- Production build успешно собирается.
- Основные пользовательские сценарии проверены.
- Подготовлены необходимые настройки production-развёртывания.
